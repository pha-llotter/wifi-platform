Overview

How it fits together

People join Nexus with their school Google email and password. The password is checked by Google, and the platform puts each person on the VLAN for their Google org unit. Visitors use Guest with keys that admins make in the dashboard.

One login: the device sends the email and password inside a TLS tunnel to FreeRADIUS. FreeRADIUS checks the password with Google Secure LDAP. Only if it's right does it ask the platform whether this person may connect, and on which VLAN. The vSZ then puts the device on that VLAN.

Part 1

Plan

Collect these before you start. Filling in the sheet below saves going back and forth between the server, Google and the vSZ.

You'll need

  • A Linux VPS with a fixed public IP address: Ubuntu Server 24.04 LTS, 1 vCPU, 1 GB RAM and 20 GB of disk is plenty.
  • DNS access for phahs.org.za, to add two records.
  • A super admin account in the Google Admin console, and access to Google Cloud for the same domain.
  • Admin access to the vSZ and to the school's firewall or router.
  • VLANs for staff, learners and guests that already reach every access point's switch port, each with a DHCP scope.
  • A PC with an SSH client. Windows 10 and 11 include ssh and scp in PowerShell.

Decide: what happens if the platform is down

If the platform stops while FreeRADIUS and Google are fine, FreeRADIUS follows FALLBACK_VLAN:

  • Empty (the default): no new logins until the platform is back. Devices already connected stay connected.
  • A VLAN number: anyone with a correct Google password gets on to that VLAN, and blocks and rules are skipped until the platform is back. If you choose this, use a restricted learner-style VLAN, never the staff VLAN.

Part 2

Prepare the Linux server

This part sets up an Ubuntu 24.04 server with key-only SSH, a firewall, automatic security updates and Docker, then puts the code and the settings folders in place.

2.1Create the server and its DNS names

  1. Create the VPS with Ubuntu Server 24.04 LTS. If the provider has its own firewall, allow the same ports as in 2.4.
  2. Add two DNS A records pointing at the server's public IP:
    • wifi.phahs.org.za: the admin dashboard.
    • radius.phahs.org.za: the certificate devices check when they log in.
  3. Check both from your PC. Each should print the server's IP:

On your PC (PowerShell)

nslookup wifi.phahs.org.za
nslookup radius.phahs.org.za

2.2First login, updates and an admin user

Log in as root (or the user your provider made). These examples call the admin user itadmin.

On the server, as root

apt update && apt full-upgrade -y
timedatectl set-timezone Africa/Johannesburg
apt install -y git unattended-upgrades
adduser itadmin
usermod -aG sudo itadmin

Copy your SSH key to the new user. If you don't have a key yet, run ssh-keygen -t ed25519 on your PC first.

On your PC (PowerShell)

type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh itadmin@SERVER_IP "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys"

Log in as itadmin with the key. Then turn off password logins and root logins:

On the server, as itadmin

sudo tee /etc/ssh/sshd_config.d/10-pha.conf >/dev/null <<'EOF'
PasswordAuthentication no
PermitRootLogin no
EOF
sudo systemctl restart ssh
sudo dpkg-reconfigure -plow unattended-upgrades    # answer Yes
Keep your current session open Before you close it, open a second SSH session as itadmin and check it works. If it doesn't, fix it from the first session.

2.3Install Docker

These are Docker's own instructions for Ubuntu. They install Docker Engine and the Compose plugin.

sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "$VERSION_CODENAME")
Components: stable
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker run --rm hello-world       # prints "Hello from Docker!"
sudo docker compose version

This guide runs Docker with sudo. Adding itadmin to the docker group would save typing, but that group is equivalent to root.

2.4Firewall

Only SSH from your own addresses, the web ports, and RADIUS from the school are let in. Allow SSH before turning the firewall on.

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from YOUR_IP to any port 22 proto tcp
sudo ufw allow 80,443/tcp
sudo ufw allow from SCHOOL_IP to any port 1812:1813 proto udp
sudo ufw enable
sudo ufw status verbose
  • Repeat the SSH line for each address you manage the server from. If your own IP changes often, use sudo ufw allow 22/tcp instead: SSH accepts keys only, so that's still safe.
  • SCHOOL_IP is the address RADIUS from the vSZ arrives from (see 4.7). Part 8 shows how to read it from the logs if you're unsure.
  • All three containers use the host's network directly, without published ports, so these ufw rules apply to them as normal. Docker's usual habit of skipping ufw for published ports doesn't come into it.

2.5Get the code onto the server

The code is public on GitHub at github.com/pha-llotter/wifi-platform, so the server can download it without a key or password. It lives in /opt/wifi-portal.

On the server

sudo mkdir /opt/wifi-portal && sudo chown $USER: /opt/wifi-portal
git clone https://github.com/pha-llotter/wifi-platform.git /opt/wifi-portal

The repo holds only code and examples. Every real setting and secret lives in /etc/wifi-portal on the server and never goes into Git.

2.6Settings folders and the two secrets

sudo mkdir -p /etc/wifi-portal/google-ldap /var/log/wifi-portal /var/lib/wifi-portal
sudo cp /opt/wifi-portal/config.example.json /etc/wifi-portal/config.json
sudo cp /opt/wifi-portal/deploy/freeradius/radius.env.example /etc/wifi-portal/radius.env
sudo chown 1000 /var/log/wifi-portal /var/lib/wifi-portal
openssl rand -hex 32     # 1: the RADIUS shared secret (vSZ ↔ FreeRADIUS)
openssl rand -hex 32     # 2: the platform token (FreeRADIUS ↔ platform)

Save both values in your password manager, labelled. The first goes on the vSZ (part 4) and in radius.env. The second goes in radius.env and config.json (part 5).

Stop here for now Don't start the containers yet. The platform needs the Google and vSZ details first. Carry on with part 3.

Part 3

Google Workspace

Education Fundamentals includes everything here. You'll end up with three things for the server: the Secure LDAP certificate and key, an OAuth client for the dashboard sign-in, and a service account key for the directory, alerts and backups.

3.1Secure LDAP client: checks passwords

  1. In the Admin console go to Apps → LDAP → Add client. Name it WiFi RADIUS.
  2. Access permissions, both for the whole domain (or every org unit that should use the WiFi):
    • Verify user credentials
    • Read user information
  3. Download the certificate. The zip holds a .crt and a .key file. Rename them ldap-client.crt and ldap-client.key.
  4. Set the client's Service status to On. It can take a few minutes, and sometimes longer, before Google accepts the certificate.
  5. Note the certificate's expiry date, shown on the client's page, and put a reminder in the calendar a month before it.

Leave access credentials (a username and password for the LDAP client) alone for now: the certificate is enough. Part 8 covers the case where they're needed.

3.2OAuth client: admin sign-in to the dashboard

  1. In Google Cloud console create a project, for example PHA WiFi.
  2. Google Auth Platform → Audience: set it to Internal, so only school accounts can sign in.
  3. Clients → Create client: type Web application, authorised redirect URI https://wifi.phahs.org.za/admin/oauth/callback.
  4. Save the client ID and client secret in the password manager.

3.3Service account: directory, alerts and backups

  1. In the same Cloud project, enable the Admin SDK API. Enable the Gmail API for alert emails and the Google Drive API for off-site backups.
  2. IAM & Admin → Service accounts → Create, with no roles. Open it, then Keys → Add key → JSON. Save the file as service-account.json.
  3. Copy the service account's client ID (a long number).
  4. In the Admin console: Security → Access and data control → API controls → Domain-wide delegation → Add new. Paste the client ID, and these scopes, comma-separated:
https://www.googleapis.com/auth/admin.directory.user.readonly,https://www.googleapis.com/auth/gmail.send,https://www.googleapis.com/auth/drive.file
  • admin.directory.user.readonly reads org units and whether an account is suspended. It's needed.
  • gmail.send sends alert emails. Leave it out if you don't want alerts.
  • drive.file uploads nightly backups. It can only see files it uploaded itself. Leave it out if you don't want Drive backups.
Your organisation may block service account keys If Google Cloud refuses to make a JSON key, the organisation policy iam.disableServiceAccountKeyCreation is on. A Cloud organisation admin can turn it off for this one project.

3.4Alert mailbox and backup folder (optional)

  • Alerts are sent as a real Workspace user, for example wifi-alerts@phahs.org.za. The service account can send as that user but can't read its mail.
  • Backups: make a Shared Drive, for example WiFi backups. Add the alert mailbox user as Content manager, make a folder in it, and copy the last part of the folder's URL. That's the folder ID.

3.5Check the org units

In Directory → Organizational units, check the exact paths for staff and learners, for example /Staff and /Students, and fill them in on the worksheet. A rule matches its org unit and everything under it.

3.6Copy the files to the server

On your PC (PowerShell), in the folder with the three files

scp ldap-client.crt ldap-client.key service-account.json itadmin@SERVER_IP:~

On the server

sudo mv ~/ldap-client.crt ~/ldap-client.key /etc/wifi-portal/google-ldap/
sudo mv ~/service-account.json /etc/wifi-portal/

Then delete the copies on your PC, keeping them only in the password manager. Part 5 sets the permissions.

Part 4

Ruckus vSZ

You'll create two RADIUS services that point at the server, the Nexus WLAN with dynamic VLANs, the Guest WLAN with Dynamic PSK, and an API account for guest keys. Then you'll open the school firewall.

Menu names The paths below are for SmartZone 6.x and 7.x. In 5.x, the RADIUS services are under Services & Profiles → Authentication and → Accounting. The field names are the same.

4.1Before you start

  • The staff, learner and guest VLANs are tagged on every access point's switch port, and each has a DHCP scope.
  • You have the server's public IP and the RADIUS shared secret from 2.6.

Use proxy mode, where the controller sends RADIUS for the APs, for both services. All RADIUS then comes from the vSZ, so FreeRADIUS only has to trust one address, and the APs' own addresses don't matter.

4.3RADIUS accounting service

Security → Accounting → Proxy → Create. Name it Nexus accounting, with the same server IP, port 1813 and the same shared secret. This is what feeds the Usage page.

4.6API account for guest keys

  1. Administration → Admins and Roles. Create a role (a user group) limited to the school's zone, with permission to manage WLANs. DPSK keys belong to a WLAN.
  2. Create an administrator wifi-portal-api in that group, with a long random password. Save the password in the password manager.
  3. Don't use a super admin account. If the platform's WLAN list in 5.4 is refused with HTTP 403, the role is too narrow: widen it one step and try again.
  4. Open the vSZ web console, click the padlock in the browser, and note the certificate's SHA-256 fingerprint. You'll compare it in 5.4.

4.7School firewall or router

DirectionFromToPortFor
OutvSZServer IPUDP 1812, 1813RADIUS logins and accounting
In (port forward)Server IP onlyvSZ management IPTCP 8443Guest keys through the vSZ API
Never open 8443 to the whole internet It's the vSZ's admin API. Limit the port forward to the server's IP. If 8443 is already open to everyone for remote management, restrict it now.

Where RADIUS comes from. With proxy mode and the vSZ at school, RADIUS reaches the server from the school's public IP, after the school's NAT. That's VSZ_ADDRESS in part 5, and the address in the ufw rule in 2.4. If the vSZ is hosted somewhere else, it's that site's public IP.

RADIUS crosses the internet protected by the shared secret, the server's firewall rule and Message-Authenticator checks. If the school firewall and the server can share a WireGuard or IPsec tunnel, sending RADIUS through it is better still.

Part 5

Finish the server and test

Fill in the two settings files, read the vSZ's certificate fingerprint and IDs, start everything, and log in with a real school account, all before any device joins.

5.1Permissions

The platform runs as uid 1000 and reads config.json, the service account key and the LDAP certificate. Only Docker, as root, reads radius.env.

cd /etc/wifi-portal
sudo chown root:1000 config.json service-account.json google-ldap google-ldap/*
sudo chmod 640 config.json service-account.json google-ldap/*
sudo chmod 750 google-ldap
sudo chown root:root radius.env && sudo chmod 600 radius.env

5.4The vSZ's fingerprint and IDs

Do these in this order. Reading the WLAN list needs the fingerprint first.

cd /opt/wifi-portal
sudo docker compose build
sudo docker compose run --rm wifi-portal node scripts/vsz-fingerprint.js /etc/wifi-portal/config.json

Compare the fingerprint with the one you noted in 4.6. If they match, paste it into dpsk.tlsFingerprint. If they don't, stop: something between the server and the vSZ isn't the vSZ.

sudo docker compose run --rm wifi-portal node scripts/vsz-wlans.js /etc/wifi-portal/config.json

This lists each zone and WLAN with its ID. Copy the school zone's zoneId, and the Guest wlanId, into config.json.

5.5Start everything

Start it in the evening FreeRADIUS restarts itself every 24 hours, counted from when it started, to pick up renewed certificates. The restart takes a few seconds, and logins in progress during it fail. Starting it after school puts that restart at night. 
cd /opt/wifi-portal
sudo docker compose up -d
sudo docker compose ps                              # three containers
sudo docker compose logs -f freeradius wifi-portal  # Ctrl+C stops watching
  • On the very first start, Caddy gets both certificates from Let's Encrypt within a minute, and FreeRADIUS waits for them.
  • After a few minutes docker compose ps should show all three as healthy.
  • If wifi-portal keeps restarting, sudo docker compose logs wifi-portal starts with Invalid config: and a list of what to fix in config.json.

5.6Check the connections

sudo docker compose exec wifi-portal node scripts/check-connections.js /etc/wifi-portal/config.json

It tries the Google directory, Secure LDAP with the client certificate, Drive, the vSZ API, and sends a test alert email (--no-email skips that). Each line says what's wrong if it fails. The dashboard has the same check under Settings → Check connections.

5.7Test a real login, without the vSZ

This logs in to FreeRADIUS on the server the way a phone does, with EAP-TTLS/PAP, and checks the certificate name. It asks for the password, which never appears on the command line. The first run builds a small test image.

cd /opt/wifi-portal
sudo ./scripts/test-login.sh a.staff.member@phahs.org.za     # expect: Accepted on VLAN 20
sudo ./scripts/test-login.sh a.learner@phahs.org.za          # expect: Accepted on VLAN 30
sudo ./scripts/test-login.sh a.staff.member@phahs.org.za     # wrong password: expect Refused

Every test shows up in the dashboard under Activity as device 02:00:00:00:00:99, with the reason for any refusal.

5.8Sign in to the dashboard

Open https://wifi.phahs.org.za/admin and sign in with an account in admin.emails. Overview → Health shows whether FreeRADIUS is calling, and the state of the Google directory, the vSZ API, backups and alerts.

5.9The first phone through the vSZ

  1. Set up one Android phone as in part 6, and connect it to Nexus with a staff account.
  2. In the dashboard, Activity shows the login and its VLAN.
  3. On the phone, check the IP address is from the staff VLAN's DHCP scope.
  4. After 10 to 20 minutes, the phone appears under Usage → Online now.

If the login is refused or nothing arrives, go to part 8.

Part 6

Devices and the pilot

Each kind of device is set up once, in a way that checks it's talking to the real server. Then run Nexus next to the current network for one or two weeks before everyone moves.

Always set devices up this way, never by hand Google can only check a plain password, so inside the encrypted tunnel the password is sent as it is (PAP). That's safe only when the device checks it's talking to radius.phahs.org.za. A device set up by hand, especially Windows with its "Continue connecting?" prompt, will give the password to a fake access point with the same name. The profiles below, and the Android and Chromebook Domain setting, prevent that.

6.1Making the Apple and Windows profiles

cd /opt/wifi-portal
sudo docker compose run --rm wifi-portal node scripts/apple-profile.js /etc/wifi-portal/config.json /var/lib/wifi-portal/Nexus.mobileconfig
sudo docker compose run --rm wifi-portal node scripts/windows-profile.js /etc/wifi-portal/config.json /var/lib/wifi-portal/Nexus.xml
sudo cp /var/lib/wifi-portal/Nexus.* ~ && sudo chown $USER ~/Nexus.*

On your PC (PowerShell)

scp itadmin@SERVER_IP:~/Nexus.* .

Neither file holds a secret, so they can be emailed or put on the intranet.

6.4Going live

  • Print the connection guide from Settings → Connection guide. Check its privacy wording against the school's ICT policy first.
  • Send the Apple and Windows profiles, and push the network to managed Chromebooks.
  • Point an uptime monitor (Uptime Kuma, or your RMM) at https://wifi.phahs.org.za/healthz.
  • Watch for directory_error alerts in the first busy week, and keep fast roaming on.

Part 7

Looking after it

Day to day, the dashboard and the alert emails tell you when something needs attention. This part covers the jobs around them.

7.1Updating the platform

After school, from /opt/wifi-portal:

git pull
sudo docker compose up -d --build
sudo docker compose ps

Only containers whose code changed are restarted. Connected devices stay connected while the platform restarts.

7.2Server updates and reboots

  • Security updates install themselves (2.2). Run sudo apt update && sudo apt full-upgrade now and then for everything else.
  • When /var/run/reboot-required exists, reboot after school or in the holidays with sudo reboot. All three containers come back by themselves.

7.3Backups: what's covered and what isn't

WhatWhere it's kept

7.4Restoring the database

cd /opt/wifi-portal
sudo docker compose stop wifi-portal
sudo mkdir -p /var/lib/wifi-portal/before-restore
sudo mv /var/lib/wifi-portal/wifi-portal.db* /var/lib/wifi-portal/before-restore/
sudo cp /var/lib/wifi-portal/backups/wifi-portal-2026-11-20-00-00-00.db /var/lib/wifi-portal/wifi-portal.db
sudo chown 1000 /var/lib/wifi-portal/wifi-portal.db
sudo docker compose start wifi-portal
  • Moving wifi-portal.db* aside also moves the database's -wal and -shm files. Left in place, they would be mixed into the restored copy.
  • For a copy from Drive, run gunzip on it first.
  • Then use Settings → Adopt keys to bring back guest keys made since that copy.

7.5Rebuilding a lost server

  1. Do 2.1 to 2.5 on a new server. If the IP changed, update both DNS records, the vSZ RADIUS services, the school's port forward and the ufw rules.
  2. Put back /etc/wifi-portal from your copy: sudo tar xzf wifi-portal-etc-DATE.tgz -C /etc. Skip 2.6: it would overwrite the restored settings with the examples.
  3. Make the data folders: sudo mkdir -p /var/log/wifi-portal /var/lib/wifi-portal && sudo chown 1000 /var/log/wifi-portal /var/lib/wifi-portal. Then restore the latest database (7.4) into /var/lib/wifi-portal.
  4. Start as in 5.5, then check as in 5.6 and 5.7.

Part 8

When something doesn't work

Start with the dashboard: Activity gives the reason for every refusal, and Overview → Health shows which connection is down. The table below covers the rest.

8.1Seeing every login in detail

sudo nano /etc/wifi-portal/radius.env      # set RADIUS_DEBUG=1
sudo docker compose up -d freeradius
sudo docker compose logs -f freeradius     # try a login, then Ctrl+C
Debug output shows passwords In debug mode FreeRADIUS prints each login in full, including the password from inside the tunnel. Use it with test accounts, for as short a time as you can, then set RADIUS_DEBUG=0 and run sudo docker compose up -d freeradius again.
