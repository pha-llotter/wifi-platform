Overview

How it fits together

People join an open network, Nexus Students or Nexus Staff. A sign-in page opens by itself, and they type their school Google email and password. Nothing is installed on the device. Google checks the password, the platform checks the person may use that network, and the device is remembered for the rest of the term. Visitors use Guest with keys that admins make in the dashboard.

One sign-in, step by step

  1. A phone joins Nexus Students. The vSZ asks the server whether this device is remembered. If it is, and the person is still allowed, the phone is online at once and nothing below happens.
  2. Otherwise the vSZ sends the phone's browser to https://wifi.phahs.org.za/, and the phone shows it in its "Log in to network" window.
  3. The person types their email and password. The platform checks the password with Google Secure LDAP, then checks the domain, blocks, the Google directory (active? which org unit?), the rules, and that this is the right network for them.
  4. The platform asks the vSZ to let the phone on, through the vSZ's Northbound Portal Interface (NBI), with a one-time ticket instead of the password. The vSZ checks the ticket with FreeRADIUS, which asks the platform.
  5. The phone is online on that network's VLAN, and the platform remembers it for 90 days.

The password goes only to Google, and is never stored or logged. The vSZ and RADIUS only ever see the one-time ticket, which works once, for two minutes.

Part 1

Plan

Collect these before you start. Filling in the sheet below saves going back and forth between the server, Google and the vSZ.

You'll need

  • A Linux VPS with a fixed public IP address: Ubuntu Server 24.04 LTS, 1 vCPU, 1 GB RAM and 20 GB of disk is plenty.
  • DNS access for phahs.org.za, to add two records.
  • A super admin account in the Google Admin console, and access to Google Cloud for the same domain.
  • Admin access to the vSZ and to the school's firewall.
  • VLANs for staff, learners and guests that already reach every access point's switch port, each with a DHCP scope and DNS.
  • A PC with an SSH client. Windows 10 and 11 include ssh and scp in PowerShell.

If the server is down

  • No new sign-ins and no reconnects on Nexus Students and Nexus Staff until the server is back. The sign-in page can't load, and remembered devices can't be checked.
  • Devices already online stay online until their session ends, at most 12 hours.
  • Guest keeps working. Guest keys live on the vSZ. Only making new keys needs the server.

Part 2

Prepare the Linux server

This part sets up an Ubuntu 24.04 server with key-only SSH, a firewall, automatic security updates and Docker, then puts the code and the settings folders in place.

2.1Create the server and its DNS names

  1. Create the VPS with Ubuntu Server 24.04 LTS. If the provider has its own firewall, allow the same ports as in 2.4.
  2. Add two DNS A records pointing at the server's public IP:
    • wifi.phahs.org.za: the sign-in page and the admin dashboard.
    • radius.phahs.org.za: FreeRADIUS needs a certificate for this name to start. Devices never see it.
  3. Check both from your PC. Each should print the server's IP:

On your PC (PowerShell)

nslookup wifi.phahs.org.za
nslookup radius.phahs.org.za

2.2First login, updates and an admin user

Log in as root (or the user your provider made). These examples call the admin user itadmin.

On the server, as root

apt update && apt full-upgrade -y
timedatectl set-timezone Africa/Johannesburg
apt install -y git unattended-upgrades
adduser itadmin
usermod -aG sudo itadmin

Copy your SSH key to the new user. If you don't have a key yet, run ssh-keygen -t ed25519 on your PC first.

On your PC (PowerShell)

type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh itadmin@SERVER_IP "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys"

Log in as itadmin with the key. Then turn off password logins and root logins:

On the server, as itadmin

sudo tee /etc/ssh/sshd_config.d/10-pha.conf >/dev/null <<'EOF'
PasswordAuthentication no
PermitRootLogin no
EOF
sudo systemctl restart ssh
sudo dpkg-reconfigure -plow unattended-upgrades    # answer Yes
Keep your current session open Before you close it, open a second SSH session as itadmin and check it works. If it doesn't, fix it from the first session.

2.3Install Docker

These are Docker's own instructions for Ubuntu. They install Docker Engine and the Compose plugin.

sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu noble stable" | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker run --rm hello-world       # prints "Hello from Docker!"
sudo docker compose version

Type the echo line as one line. If apt-get update says Malformed entry, the line was split or pasted with Windows line endings: run the echo line again. This guide runs Docker with sudo. Adding itadmin to the docker group would save typing, but that group is equivalent to root.

2.4Firewall

Only SSH from your own addresses, the web ports, and RADIUS from the school are let in. Allow SSH before turning the firewall on.

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from YOUR_IP to any port 22 proto tcp
sudo ufw allow 80,443/tcp
sudo ufw allow from SCHOOL_IP to any port 1812:1813 proto udp
sudo ufw enable
sudo ufw status verbose
  • Repeat the SSH line for each address you manage the server from. If your own IP changes often, use sudo ufw allow 22/tcp instead: with key-only SSH, that's still safe.
  • Ports 80 and 443 are open to everyone: phones load the sign-in page through them, and Let's Encrypt needs them for certificates.
  • SCHOOL_IP is the address RADIUS from the vSZ arrives from (see 4.11). Part 8 shows how to read it from the logs if you're unsure.
  • The server only connects out to the vSZ (API and NBI), so no rule is needed here for those.
  • All three containers use the host's network directly, without published ports, so these ufw rules apply to them as normal.

2.5Get the code onto the server

The code is public on GitHub at github.com/pha-llotter/wifi-platform, so the server can download it without a key or password. It lives in /opt/wifi-portal.

On the server

sudo mkdir /opt/wifi-portal && sudo chown $USER: /opt/wifi-portal
git clone https://github.com/pha-llotter/wifi-platform.git /opt/wifi-portal

The repo holds only code and examples. Every real setting and secret lives in /etc/wifi-portal on the server and never goes into Git. Keep your own copies in a folder that Git ignores, such as server-config/ in your copy of the repo.

2.6Settings folders and the two secrets

sudo mkdir -p /etc/wifi-portal/google-ldap /var/log/wifi-portal /var/lib/wifi-portal
sudo cp /opt/wifi-portal/config.example.json /etc/wifi-portal/config.json
sudo cp /opt/wifi-portal/deploy/freeradius/radius.env.example /etc/wifi-portal/radius.env
sudo chown 1000 /var/log/wifi-portal /var/lib/wifi-portal
openssl rand -hex 32     # 1: the RADIUS shared secret (vSZ ↔ FreeRADIUS)
openssl rand -hex 32     # 2: the platform token (FreeRADIUS ↔ platform)

Save both values in your password manager, labelled. The first goes on the vSZ (part 4) and in radius.env. The second goes in radius.env and config.json (part 5).

Stop here for now Don't start the containers yet. The platform needs the Google and vSZ details first. Carry on with part 3.

Part 3

Google Workspace

Education Fundamentals includes everything here. You'll end up with four things for the server: the Secure LDAP certificate, key and access credentials; an OAuth client for the dashboard sign-in; and a service account key for the directory, alerts and backups.

3.1Secure LDAP client: checks passwords

  1. In the Admin console go to Apps → LDAP → Add client. Name it WiFi RADIUS.
  2. Access permissions, both for the whole domain (or every org unit that should use the WiFi):
    • Verify user credentials
    • Read user information
  3. Download the certificate. The zip holds a .crt and a .key file. Rename them ldap-client.crt and ldap-client.key.
  4. Set the client's Service status to On. It can take a few minutes, and sometimes longer, before Google accepts the certificate.
  5. Note the certificate's expiry date, shown on the client's page, and put a reminder in the calendar a month before it.
  6. Access credentials → Generate new credentials. Save the username and password: Google shows the password once. Some tenants, including phahs.org.za, let a client with only the certificate see the org units but no users, so every sign-in would fail without them.

3.2OAuth client: admin sign-in to the dashboard

  1. In Google Cloud console create a project, for example nexus-wifi.
  2. Google Auth Platform → Audience: set it to Internal, so only school accounts can sign in.
  3. Clients → Create client: type Web application, authorised redirect URI https://wifi.phahs.org.za/admin/oauth/callback.
  4. Save the client ID and client secret in the password manager.

This is only for admins signing in to the dashboard. The WiFi sign-in page doesn't use a "Sign in with Google" button, because Google blocks its own sign-in page inside the window phones open for WiFi sign-in. It uses a plain email and password form, checked by Secure LDAP.

3.3Service account: directory, alerts and backups

  1. In the same Cloud project, enable the Admin SDK API. Enable the Gmail API for alert emails and the Google Drive API for off-site backups.
  2. IAM & Admin → Service accounts → Create, with no roles. Open it, then Keys → Add key → JSON. Save the file as service-account.json.
  3. Copy the service account's client ID (a long number).
  4. In the Admin console: Security → Access and data control → API controls → Domain-wide delegation → Add new. Paste the client ID, and these scopes, comma-separated:
https://www.googleapis.com/auth/admin.directory.user.readonly,https://www.googleapis.com/auth/gmail.send,https://www.googleapis.com/auth/drive.file
  • admin.directory.user.readonly reads org units and whether an account is suspended. It's needed.
  • gmail.send sends alert emails. Leave it out if you don't want alerts.
  • drive.file uploads nightly backups. It can only see files it uploaded itself. Leave it out if you don't want Drive backups.
Your organisation may block service account keys If Google Cloud refuses to make a JSON key, the organisation policy iam.disableServiceAccountKeyCreation is on. A Cloud organisation admin can turn it off for this one project.

3.4Alert mailbox and backup folder (optional)

  • Alerts are sent as a real Workspace user, for example wifi-alerts@phahs.org.za. The service account can send as that user but can't read its mail.
  • Backups: make a Shared Drive, for example WiFi backups. Add the alert mailbox user as Content manager, make a folder in it, and copy the last part of the folder's URL. That's the folder ID.

3.5Check the org units

In Directory → Organizational units, check the exact paths for staff and learners, for example /Staff, /IT Staff and /Students, and fill them in on the worksheet. A rule matches its org unit and everything under it, so every org unit with people who should use the WiFi needs a rule, or a parent with one.

3.6Copy the files to the server

On your PC (PowerShell), in the folder with the three files

scp ldap-client.crt ldap-client.key service-account.json itadmin@SERVER_IP:~

On the server

sudo mv ~/ldap-client.crt ~/ldap-client.key /etc/wifi-portal/google-ldap/
sudo mv ~/service-account.json /etc/wifi-portal/

Keep your copies only in the password manager or a Git-ignored folder. Part 5 sets the permissions.

Part 4

Ruckus vSZ

You'll point two RADIUS services at the server, turn on the portal interface, make the sign-in portal, then create the three networks: Nexus Students, Nexus Staff and Guest. Last, you'll open two ports on the school firewall, for the server only.

Menu names The paths below are for SmartZone 6.1 (Essentials). Other versions move some pages. If a menu isn't where this says, type its name into the search menu box at the top right of the vSZ. The field names are the same.

4.1Before you start

  • The staff, learner and guest VLANs are tagged on every access point's switch port, and each has a DHCP scope and working DNS.
  • You have the server's public IP and the RADIUS shared secret from 2.6.

Use proxy mode, where the controller sends RADIUS for the APs, for both services. All RADIUS then comes from the vSZ, so FreeRADIUS only has to trust one address, and the APs' own addresses don't matter.

4.10API account for guest keys

  1. Administration → Admins and Roles → Roles → Create. Limit it to the school's zone, with these permissions:
    • WLAN and User/Device/App: Full access. DPSK keys belong to a WLAN.
    • SZ, AP and ICX: Read.
    • Admin: none.
  2. Create an administrator wifi-portal-api with that role and a long random password. Save the password in the password manager.
  3. Don't use a super admin account. If the WLAN list in 5.4 is refused with HTTP 403, the role is too narrow: widen it one step and try again.
  4. Open the vSZ web console, click the padlock in the browser, and note the certificate's SHA-256 fingerprint. You'll compare it in 5.4.

4.11School firewall

The server needs to reach two ports on the vSZ, through the school's public IP. Forward them from the server's IP only.

DirectionFromToPortFor
OutvSZServer IPUDP 1812, 1813RADIUS: sign-ins, reconnects, usage
In (port forward)Server IP onlyvSZ, TCP 8443Outside 9443 (example)The vSZ API: guest keys. dpsk.port
In (port forward)Server IP onlyvSZ, TCP 9443Outside 9444 (example)The NBI: letting devices on. portal.nbi.port

The outside ports can be anything free. Many firewalls, including FortiGate, use 8443 for their own admin page, which is why the examples use 9443 and 9444.

On a FortiGate

  1. Policy & Objects → Addresses → Create: wifi-server, type Subnet, the server's IP with /32.
  2. Policy & Objects → Virtual IPs → Create, twice:
    • vsz-api: the WAN port with the school's public IP (or any), external IP the school's public IP, map to the vSZ's IP, Port forwarding on, TCP, external port 9443 → mapped port 8443. Under Optional filters, set the source to the server's IP.
    • vsz-nbi: the same, external port 9444 → mapped port 9443.
  3. Policy & Objects → Services → Create: VSZ-API (TCP 8443) and VSZ-NBI (TCP 9443).
  4. Policy & Objects → Firewall Policy → Create: name WiFi server to vSZ API. Fill it in as follows, then drag it above any deny policy from the WAN to that interface:
    • Incoming: the WAN port, or the SD-WAN zone if the school uses SD-WAN.
    • Outgoing: the vSZ's interface.
    • Source: wifi-server. Destination: both Virtual IPs.
    • Service: VSZ-API and VSZ-NBI. Action: Accept.
    • NAT off, and security profiles off.
Never open these ports to the whole internet They're the vSZ's admin API and portal interface. Limit both forwards to the server's IP.

Where RADIUS comes from. With proxy mode, RADIUS reaches the server from the public IP the vSZ's traffic leaves on, after the school's NAT. That's VSZ_ADDRESS in part 5, and the address in the ufw rule in 2.4. With SD-WAN and two ISPs, check it from a PC on the vSZ's network at https://ifconfig.me, and make sure the vSZ's traffic always leaves on that ISP.

Part 5

Finish the server and test

Fill in the two settings files, read the vSZ's certificate fingerprint and IDs, start everything, check every connection, and sign in with a real phone.

5.1Permissions

The platform runs as uid 1000 and reads config.json, the service account key and the LDAP certificate. Only Docker, as root, reads radius.env.

cd /etc/wifi-portal
sudo chown root:1000 config.json service-account.json google-ldap google-ldap/*
sudo chmod 640 config.json service-account.json google-ldap/*
sudo chmod 750 google-ldap
sudo chown root:root radius.env && sudo chmod 600 radius.env

After copying a new config.json with scp, run the first two lines again for it, or the platform can't read it.

5.4The vSZ's fingerprint and IDs

Do these in this order. Reading the WLAN list needs the fingerprint first.

cd /opt/wifi-portal
sudo docker compose build
sudo docker compose run --rm wifi-portal node scripts/vsz-fingerprint.js /etc/wifi-portal/config.json

Compare the fingerprint with the one you noted in 4.10. If they match, paste it into both dpsk.tlsFingerprint and portal.nbi.tlsFingerprint: the API and the NBI use the same certificate. If they don't match, stop: something between the server and the vSZ isn't the vSZ.

sudo docker compose run --rm wifi-portal node scripts/vsz-wlans.js /etc/wifi-portal/config.json

This lists each zone and WLAN with its ID. Copy the school zone's zoneId, and the Guest wlanId, into config.json.

5.5Start everything

Start it in the evening FreeRADIUS restarts itself every 24 hours, counted from when it started. The restart takes a few seconds, and sign-ins during it fail. Starting it after school puts that restart at night. 
cd /opt/wifi-portal
sudo docker compose up -d
sudo docker compose ps                              # three containers
sudo docker compose logs -f freeradius wifi-portal  # Ctrl+C stops watching
  • On the very first start, Caddy gets both certificates from Let's Encrypt within a minute, and FreeRADIUS waits for them.
  • After a few minutes docker compose ps should show all three as healthy.
  • If wifi-portal keeps restarting, sudo docker compose logs wifi-portal starts with Invalid config: and a list of what to fix in config.json.
  • After changing config.json later, sudo docker compose restart wifi-portal. After changing radius.env, sudo docker compose up -d freeradius.

5.6Check the connections

sudo docker compose exec wifi-portal node scripts/check-connections.js /etc/wifi-portal/config.json

5.8The first phone

Leave RADIUS_DEBUG=1 in radius.env for this test, so the log shows exactly what the vSZ sends. Then:

  1. On a phone, forget any old Nexus network, then join Nexus Staff. The sign-in page should open by itself within a few seconds.
  2. Sign in with a staff account. The page says You're connected.
  3. In the dashboard, Activity shows signed_in from the sign-in page, and People shows the device and the network.
  4. On the phone, check the IP address is from the staff VLAN's DHCP scope.
  5. Turn WiFi off and on. The phone should reconnect without the sign-in page, and Activity shows signed_in from a remembered device.
  6. After 10 to 20 minutes, the phone appears under Usage → Online now.

Then look at the log on the server:

cd /opt/wifi-portal
sudo docker compose logs --tail 60 wifi-portal freeradius | grep -v Status-Server

If the sign-in is refused or nothing arrives, go to part 8. When it all works, set RADIUS_DEBUG=0 and run sudo docker compose up -d freeradius.

Part 7

Looking after it

Day to day, the dashboard and the alert emails tell you when something needs attention. This part covers the jobs around them.

7.1Updating the platform

After school, from /opt/wifi-portal:

git pull
sudo docker compose up -d --build
sudo docker compose ps

Only containers whose code changed are restarted. Connected devices stay connected while the platform restarts. Sign-ins during the restart fail for a few seconds.

7.2Server updates and reboots

  • Security updates install themselves (2.2). Run sudo apt update && sudo apt full-upgrade now and then for everything else.
  • When /var/run/reboot-required exists, reboot after school or in the holidays with sudo reboot. All three containers come back by themselves.

7.3Backups: what's covered and what isn't

WhatWhere it's kept
The database: sign-ins, people, remembered devices, usage, guest keys, rulesCopied every night to /var/lib/wifi-portal/backups/ (the last 14), and to the Drive folder if set up (the last 30, gzipped).
Settings and secrets in /etc/wifi-portalNot backed up automatically. Make a copy after setup and after each change, as below.
The codeOn GitHub: github.com/pha-llotter/wifi-platform
Let's Encrypt certificatesNot needed: Caddy gets new ones by itself.
 
sudo tar czf ~/wifi-portal-etc-$(date +%F).tgz -C /etc wifi-portal
sudo chown $USER ~/wifi-portal-etc-*.tgz      # then copy it to your PC with scp

That file holds every secret. Store it encrypted, for example as an attachment in the password manager, and delete it from the server.

7.4Restoring the database

cd /opt/wifi-portal
sudo docker compose stop wifi-portal
sudo mkdir -p /var/lib/wifi-portal/before-restore
sudo mv /var/lib/wifi-portal/wifi-portal.db* /var/lib/wifi-portal/before-restore/
sudo cp /var/lib/wifi-portal/backups/wifi-portal-2026-11-20-00-00-00.db /var/lib/wifi-portal/wifi-portal.db
sudo chown 1000 /var/lib/wifi-portal/wifi-portal.db
sudo docker compose start wifi-portal
  • Moving wifi-portal.db* aside also moves the database's -wal and -shm files. Left in place, they would be mixed into the restored copy.
  • For a copy from Drive, run gunzip on it first.
  • Then use Settings → Adopt keys to bring back guest keys made since that copy. Devices remembered since that copy sign in once more.

7.5Rebuilding a lost server

  1. Do 2.1 to 2.5 on a new server. If the IP changed, update both DNS records, the vSZ RADIUS services, the two port forwards' source filter and the ufw rules.
  2. Put back /etc/wifi-portal from your copy: sudo tar xzf wifi-portal-etc-DATE.tgz -C /etc. Skip 2.6: it would overwrite the restored settings with the examples.
  3. Make the data folders: sudo mkdir -p /var/log/wifi-portal /var/lib/wifi-portal && sudo chown 1000 /var/log/wifi-portal /var/lib/wifi-portal. Then restore the latest database (7.4) into /var/lib/wifi-portal.
  4. Start as in 5.5, then check as in 5.6 and 5.8.

Part 8

When something doesn't work

Start with the dashboard: Activity gives the reason for every refusal, and Overview → Health shows which connection is down. The table below covers the rest.

8.1Seeing every request in detail

sudo nano /etc/wifi-portal/radius.env      # set RADIUS_DEBUG=1
sudo docker compose up -d freeradius
sudo docker compose logs -f freeradius     # try a sign-in, then Ctrl+C
What debug output shows Each RADIUS request in full: device addresses, the network name in Called-Station-Id, and the one-time tickets. Passwords never reach FreeRADIUS, so they never appear. It's noisy, so set RADIUS_DEBUG=0 again when you're done and run sudo docker compose up -d freeradius.
